## 1. 设计目标与约束

### 1.1 设计目标

| 目标编号 | 目标 | 量化指标 |
|:---|:---|:---|
| DG-01 | **高可用**：Token服务全年可用性≥99.9% | 年度停机<8.76小时 |
| DG-02 | **高性能**：核心API响应P99<100ms | Locust压测验证 |
| DG-03 | **高安全**：Secret Key与Token全链路加密 | 通过第三方渗透测试 |
| DG-04 | **高扩展**：支撑3年内10,000套设备接入 | 水平扩展无单点瓶颈 |
| DG-05 | **合规性**：满足NBC数据本地化与审计要求 | 通过NBC技术评估 |
| DG-06 | **多租户**：支持≥5家MFI同时接入 | 每家MFI数据隔离 |

### 1.2 设计约束

| 约束类型 | 约束内容 | 影响 |
|:---|:---|:---|
| 地域约束 | 柬埔寨网络基础设施相对薄弱，4G覆盖不均，农村以3G/2G为主 | 必须支持网络降级，SMS作为兜底通道 |
| 合规约束 | NBC要求客户敏感数据存储于柬埔寨境内或经批准的跨境中心 | AWS新加坡区域需配合数据分类策略 |
| 成本约束 | 首期预算有限，需控制云资源月度成本<$2,000 | 采用Serverless与按需实例混合策略 |
| 技术约束 | 团队以Python为主，前端以React/Flutter为主 | 技术栈选型需匹配团队能力 |
| 时延约束 | 金边至新加坡AWS区域RTT≈30ms，需优化以减少用户感知延迟 | CDN + 边缘缓存 + 数据库连接池优化 |

### 1.3 架构原则

1. **微服务优先**：按业务域拆分服务，独立部署、独立扩缩容
2. **安全内建**：Secret Key全链路加密，零信任网络，mTLS设备认证
3. **事件驱动**：支付、还款、逾期等核心事件通过Kafka异步解耦
4. **数据分层**：热数据Redis、温数据PostgreSQL、冷数据S3归档
5. **GitOps**：基础设施即代码（IaC），所有环境变更通过Git版本控制
6. **可观测性**：Metrics（Prometheus）+ Logs（OpenSearch）+ Traces（Jaeger）三位一体

### 4.2 架构决策记录（ADR）

#### ADR-001：选用FastAPI而非Django

- **状态**：已接受
- **背景**：需要高性能异步API，支撑Token生成高并发请求
- **决策**：选用FastAPI + Uvicorn（ASGI）
- **理由**：
  - 异步原生支持，单实例QPS可达Django的3-5倍
  - 自动OpenAPI文档，减少前后端沟通成本
  - Pydantic模型校验，减少样板代码
- **后果**：ORM选用SQLAlchemy 2.0（异步支持），放弃Django Admin，自建运营后台

#### ADR-002：选用AWS新加坡区域（ap-southeast-1）

- **状态**：已接受
- **背景**：柬埔寨无AWS区域，需在东南亚选择延迟最低的区域
- **决策**：AWS新加坡区域（ap-southeast-1）
- **理由**：
  - 金边至新加坡RTT≈30ms，优于东京（80ms）
  - AWS新加坡区域服务最全（MSK、EKS、ElastiCache均可用）
  - 柬埔寨本地数据中心不成熟，自建机房成本过高
- **后果**：需配合NBC数据合规要求，客户敏感数据加密存储并保留本地备份策略

#### ADR-003：选用EMQX Enterprise而非自研MQTT Broker

- **状态**：已接受
- **背景**：需要支撑1,000+设备并发MQTT连接，要求mTLS、规则引擎
- **决策**：EMQX Enterprise部署于EKS
- **理由**：
  - 开源版EMQX已支撑百万级并发，企业版增加mTLS、数据持久化、规则引擎
  - 自研Broker开发周期3个月+，且需长期维护
  - 支持柬埔寨运营商APN适配
- **后果**：需购买EMQX Enterprise License（预估$5,000/年）

#### ADR-004：选用AWS MSK而非自建Kafka

- **状态**：已接受
- **背景**：需要高可用消息总线，团队无Kafka运维经验
- **决策**：AWS MSK（Managed Streaming for Kafka）
- **理由**：
  - 全托管，自动补丁、备份、监控
  - 与AWS生态集成（IAM认证、CloudWatch日志）
  - 按需扩展，避免前期过度投入
- **后果**：MSK成本高于自建EC2集群约30%，但节省运维人力

#### ADR-005：选用PostgreSQL 15而非MongoDB

- **状态**：已接受
- **背景**：设备遥测数据为半结构化，团队考虑MongoDB的灵活性
- **决策**：PostgreSQL 15（JSONB字段存储遥测）
- **理由**：
  - Token、合同、还款等核心数据强关系型，PostgreSQL ACID保障
  - JSONB支持半结构化遥测数据，且支持GIN索引快速查询
  - RDS托管，自动备份、多可用区
- **后果**：超大遥测数据量（>1亿条）时需按时间分区（Partitioning）

#### ADR-006：选用Flutter而非React Native

- **状态**：已接受
- **背景**：安装技师App需离线功能，MFI Loan Officer App需跨平台
- **决策**：Flutter
- **理由**：
  - 性能接近原生，UI一致性优于React Native
  - 离线数据持久化（SQLite）支持成熟
  - 一套代码覆盖Android/iOS，减少维护成本
- **后果**：团队需学习Dart语言，前期上手成本略高

#### ADR-007：微服务拆分粒度——6个服务而非更多

- **状态**：已接受
- **背景**：团队规模有限（1架构师+2后端+1前端+1DevOps），过度拆分增加复杂度
- **决策**：6个微服务（Token/Device/Payment/MFI/Notification/OTA-Report）
- **理由**：
  - 每个服务对应独立业务域，数据库独立，部署独立
  - 6个服务在EKS上管理复杂度可控
  - 未来可再拆分（如Notification拆为SMS-Service + MQTT-Service）
- **后果**：初期部分服务间存在代码复用，需维护Shared Kernel库

### 7.3 API安全设计

| 安全机制 | 实现方式 | 配置 |
|:---|:---|:---|

**MFI适配器设计原则**：
- **隔离性**：每家MFI独立Adapter，故障不互相影响
- **标准化**：统一数据模型（Customer/Contract/Repayment），Adapter负责转换
- **容错性**：CBS超时/故障时，消息队列暂存，最多重试3次，间隔5分钟
- **可观测性**：每家MFI独立同步状态看板，延迟告警
